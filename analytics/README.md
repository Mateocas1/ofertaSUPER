# Analytics — dense daily series, DuckDB + dbt, basket index

Python project (uv) that turns the catalog's price observations into a dense
daily series and a published basket index. No part of the public read path
touches this project: the pipeline writes one small committed JSON and the
Next.js app renders that.

```
Postgres (price_history + offer state)
        │  scripts/export-price-series.ts        (#548 slice 1)
        ▼
date=YYYY-MM-DD/part.parquet  ──release `analytics-data`──►  analytics/data/
        │  dbt build (DuckDB)
        ▼
dim_product · dim_store · fct_price_daily
mart_product_price_variation · mart_category_price_variation
mart_basket_index_daily · mart_basket_index_monthly · mart_basket_index_vs_cpi
mart_price_movers
        │  scripts/publish_basket_index.py
        ▼
data/analytics/basket-index.json  ──►  /inflacion page (no database on read)
```

## Run it

```bash
cd analytics
uv sync
uv run dbt build --profiles-dir .          # builds from the committed sample
uv run python scripts/publish_basket_index.py --skip-build --check
```

Real data (after exporting, see the root runbook):

```bash
scripts/analytics-data.sh download analytics/data
cd analytics
uv run python scripts/publish_basket_index.py \
  --glob 'data/*/part.parquet' --source release
```

The published payload is only `status = "ready"` when there are at least two
basket months and one of them overlaps a published INDEC month. Otherwise it is
`status = "insufficient"` with **no index values**, and the page renders an
empty state instead of a one-point "index". The committed production payload is
the canonical placeholder:

```bash
uv run python scripts/publish_basket_index.py --placeholder --source release
```

`dbt build` is reproducible from a clean checkout: the default
`price_series_glob` var points at the tiny committed sample
(`sample/part.parquet`, generated by `scripts/make_sample_parquet.py`), and the
sample **page payload** used by the tests and CI lives at
`tests/fixtures/basket-index.sample.json`. Neither sample artifact is served in
production. The CI job in `.github/workflows/analytics.yml` runs the build, both
payload checks and the chart.

## The README chart

`npx tsx scripts/chart-price-evolution.ts` (repository root) renders
`assets/price-evolution.png` from the committed real snapshot
(`data/catalog-snapshot.json`): every dated observation of the 12 fixed basket
products, averaged per product and day. The chart subtitle and the README
caption name the real range and the source, and say so plainly while fewer than
seven days exist. The sample (`sample/part.parquet`, drawn by
`scripts/chart_price_evolution.py`) is a CI fixture only: it refuses to write
the README path and can never be published as the real chart.

## The dense series

One row per `(date, gtin14, store)` from the pair's first observation onward.
The catalog only records a price when it changes, so the exporter carries the
last observed offer state forward:

- `reason = observed` — the observation falls on that date.
- `reason = carried_forward` — fresh, but the last observation is from an
  earlier date.
- `reason = stale` — the last observation is older than 24 h; the value columns
  are null and `age_hours` records the gap.

Availability and promotion flags are only recorded for the offer's current
state, so they are carried only when that state is the fresh observation.
The freshness reference is `min(end of the UTC day, the export instant)`, which
keeps the daily cloud export measured against "now" and the backfill measured
against each day's end.

## The basket index

`seeds/basket_weights.csv` is the fixed Laspeyres basket: 12 real catalog
GTIN-14s with weights that sum to 1. On each date the index is
`Σ wᵢ·(pᵢ/dᵢ) / Σ wᵢ · 100`, where `pᵢ` is the product's simple average price
across the measured stores and `dᵢ` its price on the base date (the first date
whose fresh-price coverage cleared `basket_min_coverage`, 0.6). On the base date
the index reads exactly 100; below the coverage threshold it publishes null with
`index_reason` instead of a thin number.

`seeds/indec_cpi.csv` is the official INDEC IPC Nivel General Nacional (base
December 2016), monthly, with the exact source URL in each row. Refresh it only
through `scripts/fetch_indec_cpi.py`; that script fails loudly instead of
inventing values. `mart_basket_index_vs_cpi` rebases the CPI to the basket base
month so both series share an axis, and reports a null with `cpi_reason` for a
month the INDEC has not published yet.

The page payload carries a `status` (`ready` / `insufficient`) plus a
`statusNote` and the `requirements` it is missing. `publish_basket_index.py`
computes it in one place, so neither the dbt marts nor the page can invent a
number when the window is too short.

## Honest limitations

- The basket index averages prices across Carrefour, Disco and Jumbo; it is not
  a weighted-by-share shelf index.
- The basket is fixed by the seed, not by household survey weights.
- `fct_price_daily` availability and promotion columns are only meaningful for
  the freshest observation; older rows carry nulls.
- Real catalog data starts on 2026-09-28, later than the INDEC series available
  here (ends 2026-08-01), so the production payload is `insufficient` (no index
  values) until at least two basket months and one overlapping CPI month exist.
  The page explains exactly that instead of showing sample numbers.
- The README chart reads the snapshot's per-offer history, which still carries
  the 2026-09-20 bootstrap observations; the dense Parquet series (and therefore
  `basket-index.json`) starts on 2026-09-28, when the daily export began.
